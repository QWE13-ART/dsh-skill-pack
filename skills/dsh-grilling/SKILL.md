# DSH 开工前对齐访谈（Grilling）

> 移植自 mattpocock/skills（MIT）的 `grilling`（访谈原语）+ `grill-me`（用户入口）。
> 它修的是第一失败模式：**"Agent 没做我想要的"**——你以为 AI 懂了，看到成品才发现
> 它完全没理解你。对齐成本远低于返工成本。README 原话："Use them _every_ time
> you want to make a change."

## 一、核心原则

1. **开工前对齐，不带着误解干活**——任务越模糊，访谈越要充分；"没人确切知道自己想要什么"。
2. **追问式访谈，一轮一问**——一次只问一个具体问题，等回答，更新理解，再问下一个。
   不是聊天，是结构化的需求挖掘。
3. **设计树全分支解决**——把任务理解成一棵设计树：先**广度优先铺开**（把有哪些分支问出来），
   再**深度优先逐个解决**（每个分支追到"明确到可以开工"）。
4. **绝不替用户回答**——agent 可以提出候选方案供选择，但最终答案来自用户。
   自己问自己答 = 访谈机制已坏。
5. **问具体问题，不开放式**——"这个模块的输入输出是什么" 优于 "还有什么要补充吗"。
6. **访谈产物落地**——问完把对齐结论写成短摘要（见「报告格式」），供后续会话复用，
   不重复访谈同一个问题。

## 二、触发条件

| 时机 | 场景 |
|---|---|
| 接到新任务 | 任何需要动手的任务，开工前（即使看起来很清楚）|
| 计划/设计/改动前 | 用户描述了一个目标，但实现路径有多个可能 |
| 需求含糊时 | 关键词缺失（目标对象/边界/验收标准/约束任何一个不清楚）|
| 用户主动要求 | "你先问问我再做" / "搞清楚需求" / "别急着写" |
| 对接子智能体前 | 要把任务派给 OpenHands / 子智能体前，先把任务问清楚（派错任务浪费更狠）|

**例外**：纯查询/翻译/一句话小请求，问 1-2 个关键问题或直接确认即可，不做完整访谈。

## 三、访谈流程（Grilling Loop）

### Phase 0：明确访谈目标（30 秒）
- 复述理解：**"我理解你要做的是：<一句话>。对吗？"**——先确认大方向
- 用户纠正 → 以纠正后的为准重新复述
- 大方向确认后进入 Phase 1

### Phase 1：广度优先铺开（BFS——把设计树的分支问出来）
- 围绕任务目标，把**所有维度**扫一遍，每维度一个问题：
  - **目标**：最终要交付什么（文件/功能/行为）？
  - **对象**：涉及哪些模块/文件/数据？
  - **边界**：明确不做什么？（不做 X 和做 Y 一样重要）
  - **验收**：怎么算完成？（可验证的证据是什么）
  - **约束**：技术栈/环境/时间/兼容性限制？
  - **用户背景**：这是给谁用的？什么场景？
- 用户回答中冒出的新分支 → 记入待问队列（BFS 队列）
- 直到**没有新维度浮现** → 进入 Phase 2

### Phase 2：深度优先逐个解决（DFS——每个分支追到"可开工"）
- 从待问队列取分支，逐个追问到解决：
  - **解决 = 明确到可以直接开工**（能说出具体做什么、怎么做、产出什么）
  - 每个分支循环：`问 1 个具体问题 → 用户答 → 更新理解 → 验证理解（"所以你的意思是 X？"）→ 解决则下一个分支`
- 分支解决时**顺手确认边界**："还有没有相关的 X 需要考虑？"
- 所有分支解决 → 访谈完成

### Phase 3：对齐摘要（每次访谈必做）
- 把结论写成 ≤15 行摘要（见「报告格式」），**先给用户过目**：
  - 用户确认 → 开工
  - 用户补充 → 更新摘要再确认
- 摘要存到会话/任务上下文，后续步骤以此为唯一需求源

## 四、问题质量规则

- ✅ 一题一问（多问 = 用户只答最后一个）
- ✅ 具体可答（给出选项："A、B、C 哪种？"比开放问好答）
- ✅ 用领域语言问（优先用 dsh-memory §4 的词汇表，见联动）
- ✅ 验证式追问（"所以你的意思是 X，对吗？"——确认理解而非假设）
- ❌ "还有什么要补充吗"（开放式大问 = 得不到信息）
- ❌ 连续追问不停（用户已给足信息就停止，访谈不是审问）
- ❌ 替用户做决定（候选方案可以给，答案必须用户给）

## 五、终止条件（满足任一即停）

1. **设计树全部分支 resolved**——每个分支都明确到可开工
2. 用户说"就这样/够了/开始吧"
3. 剩余模糊点**明确标注为待定**（写进摘要的「待确认」），不阻塞主体开工
4. 用户已给足信息，继续问是骚扰（体感：用户开始重复答案）

## 六、反模式（违反即失败）

- ❌ 不问就开工（对齐失败第一来源）
- ❌ 问 2-3 个问题就停（只铺开没解决，误解仍在）
- ❌ 自己问自己答（替用户脑补需求）
- ❌ 问完不留摘要（下次会话重新问一遍，用户烦）
- ❌ 带着摘要开工后擅自改需求（需求变更必须回访用户）

## 七、报告格式（对齐摘要，强制）

```markdown
## 对齐摘要
- 目标：<一句话>
- 交付物：<具体文件/功能/行为>
- 范围：<做哪些> | 边界：<明确不做的>
- 验收标准：<可验证的证据>
- 约束：<技术栈/环境/时间等>
- 待确认：<未解决但先不阻塞的项>
- 确认状态：<用户已确认 / 待用户确认>
```

## 八、与其他 skill 联动

- **dsh-memory §4**：访谈中出现的领域术语 → 同步更新项目词汇表（新词记定义、
  旧词标歧义）；问题优先用词汇表术语问（grill-with-docs 的模式）
- **dsh-subagent-orchestration**：派子智能体任务前先访谈——把对齐摘要作为任务描述的核心，
  "派错任务浪费更狠"
- **dsh-verification**：验收标准从对齐摘要来——验证器验证的是"用户确认过的验收标准",
  不是 agent 自己理解的
- **dsh-subagent-orchestration**：委派清单的任务描述 = 对齐摘要展开

## 九、质量红线

- ❌ 未访谈就开工（除非用户明确说不用）
- ❌ 替用户回答设计问题
- ❌ 摘要未经用户确认就执行
- ❌ 访谈记录不落盘（下次重复问）
- ❌ 用开放式问题糊弄（必须具体）
