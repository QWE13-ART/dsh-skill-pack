# 验证审查（一体化）

三种模式，先选对再执行：

| 场景 | 模式 | 小节 |
|---|---|---|
| 任务声称完成 / 修复后 / 委派回收 / 重要答案前，验证产物真实且可执行 | **A 产物验证**（防假完成）| §A |
| 大任务收尾 / 重要结论给出前，派子智能体独立审计防自评盲区 | **B 外部审计** | §B |
| 审查代码/改动/PR/分支（合规 + 对需求）| **C 代码审查**（双轴）| §C |
| 完成任务后主动请求他人审查 | **D 请求审查** | §D |
| 收到审查意见后正确接收与实施 | **E 接收审查** | §E |

> 组合用法：C 做第一遍（质量双轴），A 独立复验做第二遍（产物是否真实存在且可执行）。B 用于大任务收尾的兜底。

## §A 产物验证（防假完成）

> 融合 verifier.py（5 类验证器 + 预检/后验分离）+ _attach_self_verify（产物可执行校验 + 工具失败检查 + 降级上抛）+ _qa_self_correct（环境反馈纠错）+ 社区 validate-agent（完成≠达成目标）+ execution-verifier（硬证据原则）。

### A1. 核心原则

1. **完成 ≠ 达成目标**——22% 的任务静默失败、67% 的修复引入新问题、41% 的延迟任务从未执行。声称"完成"只是起点，验证才是终点。
2. **无证据 = 无进展**——只接受硬证据：文件变化、输出内容、系统状态、事件流。没有可验证的证据，就等于没做。
3. **验证结果而非动作**——"调用了工具"≠"做对了"。验证最终产物，不是过程动作。
4. **只读验证，绝不二次写**——验证器只查状态/读回，不修改任何东西；失败重试只重执行原动作（最多 1 次），不"顺手修一下"。
5. **单变量修改**——修复时每次只改一件事（单变量 71% 干净 vs 多变量 18% 干净）。
6. **存在 ≠ 可解析**——文件存在且非空还不够，还要**语法/格式级校验**：`.py→ast.parse`、`.json→json.loads`，解析失败 = 假完成（产出不可用）。
7. **动作失败也是失败**——执行期间任何工具调用失败（calls ok=false）都记入 failed_checks，与产物问题同等对待；只读验证但**可复核**：验证失败的结果**降级上抛**（不改判定，但提示调用方复核），绝不静默吞掉。

### A2. 触发条件

| 时机 | 场景 |
|---|---|
| 任务声称完成时 | 自己干活结束，验收前 |
| 修复问题后 | 修完 bug 强制验证（30 秒内），检查是否引入新问题 |
| **委派回收时** | OpenHands / GPT Researcher 返回结果，收下前 |
| 提供重要答案前 | 涉及文件/数字/承诺的关键答复 |

🔴 **机械硬触发器（2026-08-31 补，全部来自真实翻车；上表是"时机"，这三条是"客观可检查条件"）**

上表的触发条件是**我判断"这算不算重要"**——而判断力正是失灵的那一环（实测：本技能与
另 4 个反幻觉技能在一整个 65 轮会话里**触发 0 次**，4 个可拦的错一个没拦）。
所以补三条**不需要我判断**的条件：

| 机械条件（客观可查） | 必须做什么 | 真实翻车 |
|---|---|---|
| ① 我准备说 **"已改 / 已修 / 已生效 / 已落地"** | `grep` 到那行代码 **+** 跑出变绿的测试。**改了文档/注释/配置 ≠ 改了代码** | "6 个借鉴点已落地"→ 实际只 1 个 |
| ② 我准备把**某条命令的回显**当结论 | 回显只证明"这条命令这样输出"。**"删除/写入/启停"类必须再查一次目标状态** | `codegraph uninit` 弹确认、`EXIT=0`、**什么都没删** |
| ③ 我准备说**某测试/某套件"变绿了"** | 先确认它**真的断言了行为**——空跑、全 skip、fixture 与被测正则不匹配都会给绿灯 | 我的 fixture 写 `"三项改动已全部生效"`，而正则匹配 `已生效`，"全部"把它劈开了 |

🔥 **④ 探针不能比被测环境宽松。** fake mock / 放水的 `get: () => undefined` / 只扫一个
目录的检查脚本，全部等于**没测**。**判据要先 dump 真实数据的形态分布，再写**——
不要按"我能想到的形态"写正则。这是本机复发 **8 次**的头号根因
（`~/.dsh/AGENTS.md` §0.2 有完整清单）。

🔥 **⑤ 声明"某判据/规则有效"之前，必须做前后对照量化。** 只写规则不测效果 = 假设有效。
可做的最便宜实验：找到规则落地的那一轮，比对前后的违反率与峰值
（实例：`pwsh`-2 规则 63% → 30%，峰值 30 → 4）。

### A3. 验证器（按类型选择）

**1. file 验证器（最常用，含产物可执行校验）**
- 产出文件**存在？可读？内容非空？**（`glob` 找 + `read` 读）
- **读回比对**：文件实际内容与声称的一致（引用的数字/结论能在文件里找到）
- **语法/格式级校验**（按扩展名，最多校验前 3 个产物）：
  | 扩展名 | 校验动作 | 失败 = 假完成 |
  |---|---|---|
  | `.py` / `.pyw` | 读入后 AST 语法解析 | 语法错误 → FAIL |
  | `.json` | `json.loads` 完整解析 | 解析失败 → FAIL |
  | `.md` / `.html` / `.txt` / `.csv` | 读头 4KB 判非空 | 空文件 → FAIL |
  | 其他 | 文件存在即可 | — |
- 文件路径存在但内容为空 = fail；**存在但语法错误 = fail（产出不可用）**

**2. retrieval 验证器**：声称"找到了 X / 检索到 Y" → 用搜索复检关键词命中；声称的记忆确实在记忆库里。

**3. system 验证器**：声称"服务已启动 / 进程在跑 / 端口开放" → 查进程/端口/服务状态；声称"命令执行成功" → 检查退出码/输出。

**4. browser 验证器**：声称"网页可访问" → URL 可达性探测；声称"页面内容包含 X" → 抓取复检。

**5. reminder 验证器（跨会话承诺）**：跨会话承诺记录到 `E:\DSH-Data\.dsh\evolution\promises.md`；48 小时过期机制；到期未完成 → 主动报告，不静默丢弃。

**6. 执行期工具失败检查（动作层证据）**：验证产物之外，**回看本次任务的工具调用记录**——任何 `ok=false` 的调用 → 记为 failed_checks：
```json
{"kind":"tool_failure","tool":"<工具名>","op":"<操作>","issue":"<错误摘要前 120 字>"}
```
工具失败数量 ≥2 且与产物问题相关 → 高度怀疑假完成，报告里显式列出。与产物校验分开计数，但**同样参与判定**。

**7. 结论对照验证器（语义层防说谎）**
> 治"模型自述 ≠ 事实"最硬的一层：**自述结论与产物实际内容逐条对照**。执行层看"动作有没有发生"，本验证器看"结论站不站得住"。
- **适用时机**：汇报"我改了 X / 实现了 Y / 结果是 Z"之前，尤其涉及文件改动、数字、承诺、修复声明时。
- **对照动作**（对每条自述结论逐条执行）：
  | 自述结论类型 | 对照方式 | 不通过 = 疑似说谎 |
  |---|---|---|
  | "改了文件 X 的 A 处" | 读回 X，在对应位置找 A 的实际改动 | 找不到 → FAIL |
  | "新增了函数/接口 F" | 在产物中搜索 F 的定义（符号级）| 无定义 → FAIL |
  | "数字/统计是 N" | 在产物/输出中找 N 的来源（计算或引用）| 无来源 → FAIL |
  | "测试通过了" | 复跑相关测试（或查测试输出记录）| 无通过记录 → FAIL |
  | "服务/进程已启动" | 查进程/端口（system 验证器）| 未运行 → FAIL |
- **交叉采样自检**（SelfCheckGPT 思路，零成本）：关键结论换角度自问"这个结论对吗？证据是什么？"——两次独立推理答案分歧 → 标注**"不确定，需复核"**，不得包装成确定结论。
- 对照失败的结论 → 进 failed_checks（`{"kind":"claim_mismatch","claim":"<自述>","evidence":"<实际>","issue":"<差异>"}`），与产物问题同权参与判定。
- **诚实优先**：无法指认证据的结论必须显式说"未验证"，禁止模糊成"已完成"。

### A4. 降级上抛语义（degraded_upload）

验证未全过 ≠ 结果全废——但**必须显式标注，绝不静默吞掉**：

| 情况 | 行为 |
|---|---|
| 产物校验 + 工具检查全过 | 正常上抛（PASS）|
| 部分校验失败，但结果可能仍有参考价值 | **降级上抛**：判定仍 FAIL，报告标注 `degraded: true` + 失败项清单，提示调用方复核后再采信 |
| 验证过程自身异常（工具不可用等）| 标注 `degraded: true` + 原因，**不阻断上抛**（验证器故障 ≠ 任务失败）|

铁律：**验证失败的结果必须带着 degraded 标记交付，不允许"顺手改一下再验证"**（修正确性 → 重跑原动作 → 重新验证）。

### A5. QA 自纠正（环境反馈纠错）

当**当前角色是 QA/质检/评审/测试类**（或用户要求复核）且验证失败时：
1. 收集环境反馈：校验错误（语法/格式/空文件）+ 工具失败（issue 摘要），最多取 5 条
2. 调一次 LLM 生成**可执行的修正建议**（≤3 条，每条约 40 字），输入：`你是 QA 复核角色。以下产物自验证未通过，请给出可执行的修正建议（不超过 3 条，每条约 40 字）：任务：<任务描述前 200 字> 验证问题：<失败项清单> 产物摘要：<内容前 200 字>`
3. 建议挂到报告 `qa_feedback` 字段（含 `env_feedback: true`），**只给建议不代改**
4. LLM 不可用/异常 → 静默跳过（降级，不阻断验证主流程）
**纠错闭环**：QA 建议 → 执行者按「单变量修改」修 → 重新验证（同一问题最多 3 次）。

### A6. 委派场景专用验证

| 子智能体 | 验证手段 |
|---|---|
| OpenHands | `get_result`（ActionEvent 流提取，剔除 finish/think 后无真实动作=报假）+ `audit_conversation` |
| GPT Researcher | 核对报告来源列表 + 关键结论与来源一致性 |

### A7. 验证流程（6 步）

```
1. 声明验证项   → 要验证什么（"报告文件存在且含数据表"）
2. 选验证器     → 对应类型（file/retrieval/system/browser/reminder）
3. 执行只读验证 → 不修改任何东西；file 类加语法/格式级校验
4. 检查执行期   → 回看工具调用记录，工具失败记 failed_checks
5. 判定         → pass / fail + 证据（具体路径/内容片段）；未全过 → degraded 标注
6. fail 处理    → QA 角色先生成修正建议 → 修复（单变量修改）→ 重新验证（同一问题最多 3 次）
```

### A8. 报告格式（强制）

```markdown
## 验证报告
- 验证项：<要验证什么>
- 验证器：<file/retrieval/system/browser/reminder + 委派专用>
- 证据：<具体路径 / 内容片段 / 事件流记录>
- 语法校验：<通过 / 失败：哪条规则（ast/json/非空）>
- 工具失败：<无 / 失败清单（tool+op+issue）>
- 判定：PASS / FAIL（degraded: true 时注明）
- QA 建议：<qa_feedback，仅 QA 类角色失败时>
- 置信度：<高/中/低 + 理由>
```

**判定规则**：
- 无证据 → 直接 FAIL（不接受"应该没问题"）
- 证据与声称不符 → FAIL（读回比对不一致）
- 产物语法/格式校验失败 → FAIL（存在 ≠ 可解析）
- 执行期工具失败 ≥1 → 计入 FAIL 项（记 failed_checks）
- 委派结果未过 audit → FAIL（不信子智能体自述）
- 未全过但结果可参考 → FAIL + degraded 标注上抛（不静默吞掉）

## §B 外部审计（防自评盲区）

> 起因：2026-08-27 真实会话收尾时，声称本机有"13 个 vision_* 工具"，外部审计员核了同一个 listTools 输出发现是 **15 个**——漏了 3 个。**拿了权威输出也没读完。** 这个错误自己永远发现不了。

### B1. 铁律一：自评不可信

**这不是谦辞，是实测结论。** 无法在自己的认知回路里发现信息遗漏、推理越界和事实错误——因为错误正是认知回路的一部分。

| 错误类型 | 例子 | 为什么自己发现不了 |
|---|---|---|
| 信息遗漏 | 500KB listTools 只读了前 80% | 以为"读完了" |
| 推理越界 | "模型不收图 → 我不能看图" | 越界在前提里，从未被说出口 |
| 计数错误 | "13 个 vision 工具" | 抄了前 12 行，末尾 3 行没看到 |

**唯一解法：独立审计。** 同一个数据源，换一个 agent 完整读一遍。

### B2. 触发时机

**必须**在以下时刻触发审计：1. **给用户重要结论前**（尤其含数字、事实性声称）；2. **大任务收尾**（修 bug、加功能、配置变更后）；3. **会话切换前**（转向不同任务）；4. **准备说"完成了"之前**；5. **被用户指出错误后**（补审+修复）。

### B3. 审计模板

```txt
你是一个严格的 AI agent 行为审计员。请审计一个真实发生的工作会话，输出客观评估。

## 审计范围
- 会话中声称的**所有事实性结论**（数字、路径、状态、计数）
- 推理链条是否**每一步都有硬证据**（不是"exit 0 = 做成了"）
- 是否存在**推理越界**（把 A 报错推成 B 能力缺失）
- 是否存在**信息遗漏**（拿了权威输出但没读完）

## 核查方法
1. 对我提到的每个数字/路径/状态，用**引用的数据源自身**重新验证
2. 对每个"X 不存在"或"X 不可用"的断言，检查是否满足硬证据要求
3. 对每个推理链，检查中间结论是否隐含了未经验证的前提

## 输出格式
1. 事实核查：逐条列出我声称的事实，标注 ✅/❌/⚠️
2. 推理链审计：逐条列出推理，标注越界点
3. 关键单点失误：一条，说清性质和代价
4. 评分与扣分明细
5. 重来一次的最优路径
```

**审计模板必含的一条（2026-08-27 补，这条缺失导致最大错误逃过首轮审计）**——在审计任务包里**逐字加上**：

```
【归属核验】报告里每一条"X 正常 / X 故障 / X 的真因是…"的结论，
请核查它是否在 X 的【真实执行路径】上取证：
1. 用 tools_schema <X> 拿 description 原文；
2. 去各候选插件源码反查，确认谁逐字命中；
3. 报告作者引用的源码文件 / 日志文件，是否属于那个插件；
4. 若不属于 → 该结论的证据无效，请明确标注"证据测错代码路径"。
另请核查引用的日志是否真的记录 per-call 事件，不记录的日志不能用来证实或证伪单次调用。
```

**为什么必须写进模板**：首轮审计只核了数字（13 vs 15），放过了"这 15 个工具由谁实现"——那才是根本错误。**核数字能抓事实错误，核归属才能抓推理链错误。**

### B4. 审计结果落地

审计发现的错误必须**立即修正**到持久载体（AGENTS.md / 技能 / 配置）：1. `edit` 修正错误内容和数字；2. 在修正处标注**审计纠正**来源（如 `[审计纠正：实际 15 个，含 three omitted]`）；3. 错误涉及存在性否定（"本机没有 X"）→ 检讨是否触发了护栏；4. 错误是推理越界 → 检讨是否漏了"能力事实只能查询"铁律。
**修正后不意味着审计结束。** 同一审计员第二次审计仍发现同类错误 → 修补没到位，追查根因。

## §C 代码审查（两轴并行）

> 移植自 mattpocock/skills（MIT）的 `code-review`。它修的是审查最常见失败：**单一视角漏报**。一个 diff 可能合规但做错了需求（Standards pass, Spec fail），也可能做对了需求但破坏了项目约定（Spec pass, Standards fail）。两轴并行 + 分开报告，防止一轴掩盖另一轴。

### C1. 两轴定义

对用户给定的固定点（commit/分支/tag/merge-base）到 HEAD 的 diff，跑两条独立的轴：
- **Standards 轴**：代码是否符合仓库记录的编码规范？
- **Spec 轴**：代码是否忠实实现了来源 issue/spec 要求的东西？
两轴**各自用独立子智能体**跑（上下文不互相污染），主智能体最后聚合。

### C2. 流程

**1. 钉住固定点**：用户说的固定点是什么就用什么（commit SHA、分支名、tag、`main`、`HEAD~5` 等）。没指定就问。一次性捕获 diff：`git diff <fixed-point>...HEAD`（三点式，对比 merge-base）。同时记 commit 列表：`git log <fixed-point>..HEAD --oneline`。继续前先确认固定点可解析（`git rev-parse <fixed-point>`）且 diff 非空。坏 ref 或空 diff 应在此失败，而不是在两个并行子智能体里失败。

**2. 找 Spec 来源**：按序找：1. commit 消息里的 issue 引用（`#123`、`Closes #45` 等）；2. 用户作为参数传的路径；3. `docs/`、`specs/`、`.scratch/` 下匹配分支名/功能名的 spec 文件；4. 找不到就问用户。若说没有，**Spec 子智能体跳过**并报 "no spec available"。

**3. 找 Standards 来源**：仓库里任何记录"代码该怎么写"的东西：`CODING_STANDARDS.md`、`CONTRIBUTING.md`、`AGENTS.md`、`CLAUDE.md`、`.workbuddy` 下的规范文件等。在仓库文档之上，Standards 轴**始终携带 smell 基线**（Fowler《重构》第 3 章固定代码坏味道集，仓库啥都没记录也适用）。两条约束：**仓库覆盖基线**（仓库明确记录的标准永远赢）；**永远是判断**（每个 smell 是标注的启发式，不是硬违规，工具已强制的跳过）。

每个 smell 读法是 *是什么* → *怎么修*；对照 diff 匹配：
- **Mysterious Name 神秘命名**：函数/变量/类型名看不出做什么 → 改名；想不出诚实名字说明设计浑浊。
- **Duplicated Code 重复代码**：同一逻辑形状出现在多个 hunk/文件 → 抽取共享形状。
- **Feature Envy 依恋情结**：方法访问别的对象数据比自己的多 → 移到它依恋的数据上去。
- **Data Clumps 数据泥团**：同样几个字段/参数老是一起出现 → 打包成一个类型。
- **Primitive Obsession 基本类型偏执**：基本类型/字符串顶替了该有自己的类型的领域概念 → 给它自己的小类型。
- **Repeated Switches 重复 switch**：同一类型上的同一 `switch`/`if` 级联反复出现 → 多态替换或共享 map。
- **Shotgun Surgery 霰弹式修改**：一个逻辑改动被迫散落在很多文件 → 把一起变的东西聚进一个模块。
- **Divergent Change 发散式变化**：一个文件/模块因几个不相关原因被改 → 拆开，让每个模块只为一个原因变。
- **Speculative Generality 投机性泛化**：为 spec 没有的需求加的抽象/参数/hook → 删掉，出现真实需求前内联回去。
- **Message Chains 消息链**：长 `a.b().c().d()` 导航 → 把行走藏到第一个对象的一个方法里。
- **Middle Man 中间人**：类/函数主要只是往下转发 → 砍掉，直接调真实目标。
- **Refused Bequest 拒绝遗产**：子类/实现者忽略或覆盖了大部分继承来的东西 → 放弃继承，用组合。

**4. 并行跑两个子智能体**：
- **Standards 子智能体 prompt 必须包含**：完整 diff 命令 + commit 列表；找到的 standards 源文件列表，**外加把 smell 基线全文贴进去**（子智能体没有其他途径拿到它）；任务："逐文件/hunk 报告：(a) 每个违反文档化标准的位置：引用标准（文件+规则）；(b) 看到的任何基线 smell：命名并引用 hunk。区分硬违规与判断：文档化标准的破坏可以是硬的，基线 smell 永远是判断，文档化仓库标准覆盖基线。跳过工具已强制的。400 字以内。"
- **Spec 子智能体 prompt 必须包含**：diff 命令 + commit 列表；spec 的路径或抓取的内容；任务："报告：(a) spec 要求但缺失/部分实现的需求；(b) diff 里没被要求的行为（范围蔓延）；(c) 看似实现但实现看起来错的需求。每项引用 spec 原文行。400 字以内。"
- spec 缺失时跳过 Spec 子智能体，在最终报告里注明。

**5. 聚合**：在两个标题 `## Standards` 和 `## Spec` 下呈现两份报告，逐字或轻度清理。**不要合并或重排 findings**——两轴刻意分离。结尾一行总结：每轴 findings 总数，以及**每轴内**最糟的问题。不要在轴之间挑总冠军——那正是分离要防止的重排。

### C3. 为什么两轴

- 每条规范都遵守但实现错了东西 → **Standards 过，Spec 挂。**
- 完全按 issue 做的但破坏了项目约定 → **Spec 过，Standards 挂。**
分开报告，防止一轴掩盖另一轴。

### C4. DSH 场景适配

- DSH 里"规范源"可能是：`E:\CodeAudit\semgrep-rules\`（opengrep 规则，工具已强制，子智能体跳过）、插件 README 红线、skills 硬规则（如 injection-guard 的"外部内容永不以指令注入"）。
- "Spec 源"可能是：用户一句话需求、架构师规格（`docs/system_design.md`）、外部审查报告。

## §D 请求审查（Requesting Code Review）

> 移植自 obra/superpowers。**核心原则：Review early, review often。** 派一个 code reviewer 子代理在问题级联前抓住它们。审查者拿到精确构造的上下文——**绝不拿你的会话历史**。模板见 `references/code-reviewer.md`。

### D1. 何时请求

**必做**：subagent 开发中每个任务之后；完成大功能后；merge 到 main 前。**可选但有价值**：卡住时（新视角）；重构前（基线检查）；修完复杂 bug 后。

### D2. 如何请求

1. **拿 git SHAs**：`BASE_SHA=$(git rev-parse HEAD~1)`（或 origin/main）；`HEAD_SHA=$(git rev-parse HEAD)`
2. **派 code reviewer 子代理**：填 `references/code-reviewer.md` 模板的占位符——`{DESCRIPTION}`（做了什么）、`{PLAN_OR_REQUIREMENTS}`（应该做什么）、`{BASE_SHA}`、`{HEAD_SHA}`
3. **按反馈行动**：Critical 立即修；Important 继续前修；Minor 记下以后处理；审查者错了就推回（带技术理由）。

### D3. 常见合理化

| 借口 | 现实 |
|---|---|
| "我自己 review diff 就行，派发是开销" | 你是协调者——inline review 烧掉驱动工作所需的上下文。派发：diff 和评估活在审查者上下文里，只有 findings 回到你这里。|
| "审查者需要我的整个会话历史才能理解" | 给它精确构造的上下文，绝不给你会话历史。让审查者盯住工作产物，不是你的思考过程。|

### D4. 红旗

**Never**：因为"简单"跳过审查；忽略 Critical；带着未修的 Important 继续；和有效技术反馈争论。**审查者错了**：用技术理由推回、展示证明它工作的代码/测试、要求澄清。

## §E 接收审查（Code Review Reception）

> 移植自 obra/superpowers。**核心原则：先验证再实施，先问再假设。技术正确性高于社交舒适。**

### E1. 响应模式

```
WHEN receiving code review feedback:
1. READ: 完整读反馈，不反应
2. UNDERSTAND: 用自己的话重述需求（或问）
3. VERIFY: 对照代码库现实核查
4. EVALUATE: 对 THIS codebase 技术健全吗？
5. RESPOND: 技术确认或带理由的推回
6. IMPLEMENT: 一次一项，每项都测
```

### E2. 禁止回复

**NEVER**："You're absolutely right!"（指令文件违规）· "Great point!" / "Excellent feedback!"（表演性）· "Let me implement that now"（验证之前）。
**INSTEAD**：重述技术需求 · 问澄清问题 · 错了就带技术理由推回 · 直接开干（行动 > 言语）。

### E3. 处理不明反馈

```
IF any item is unclear:
  STOP - 先别实现任何东西
  ASK for clarification
WHY: 条目可能相关。部分理解 = 错误实现。
```
例：用户说"修 1-6"，你懂 1,2,3,6 不懂 4,5。❌ 先做 1,2,3,6 再问 4,5。✅ "我理解 1,2,3,6。4 和 5 需要澄清再继续。"

### E4. 来源特定处理

**来自人类伙伴**：可信——理解后实施；范围不清仍要问；无表演性同意；直接行动或技术确认。
**来自外部审查者**（实施前检查）：1. 对 THIS codebase 技术正确吗？2. 破坏现有功能吗？3. 现在这样实现的原因？4. 所有平台/版本可用吗？5. 审查者理解完整上下文吗？
若建议看似错 → 带技术理由推回。若不能轻易验证 → 明说："没有 [X] 我验证不了。该 [调查/问/继续] 吗？" 若与人类伙伴先前决定冲突 → 先停下与伙伴讨论。

### E5. YAGNI 检查（对"专业"功能）

```
IF reviewer suggests "implementing properly":
  grep codebase for actual usage
  IF unused: "这个 endpoint 没被调用。删掉它（YAGNI）？"
  IF used: Then implement properly
```

### E6. 实施顺序

```
FOR multi-item feedback:
  1. 先澄清任何不明项
  2. 然后按序实施：阻塞问题（破坏/安全）→ 简单修复（typo/import）→ 复杂修复（重构/逻辑）
  3. 每项单独测试
  4. 验证无回归
```

### E7. 何时推回

建议破坏现有功能 / 审查者缺完整上下文 / 违反 YAGNI（未用功能）/ 对该栈技术错误 / 遗留兼容原因 / 与人类伙伴架构决定冲突。**怎么推回**：用技术理由不防御性；问具体问题；引用工作的测试/代码；架构问题拉伙伴进来。若你对公开推回不舒服：说出这个张力，然后告诉伙伴你看到的问题。

### E8. 承认正确反馈

```
✅ "Fixed. [改了什么的简述]"
✅ "Good catch - [具体问题]。Fixed in [位置]。"
✅ [直接修并在代码里展示]
❌ "You're absolutely right!" / "Great point!" / "Thanks for catching that!" / 任何感谢表达
```
**为什么不说谢谢**：行动说话。直接修。代码本身显示你听到了反馈。**要写"Thanks"时：删掉它，陈述修复。**

### E9. 优雅纠正自己的推回

```
✅ "You were right - I checked [X] and it does [Y]. Implementing now."
✅ "Verified this and you're correct. My initial understanding was wrong because [reason]. Fixing."
❌ 长道歉 / 为推回辩护 / 过度解释
```
陈述事实，继续走。

## 质量红线（本技能）

- ❌ 验证时二次写（验证器只读）
- ❌ 多变量同时修改（单变量铁律）
- ❌ 用"我确认过了"代替证据（必须有具体路径/片段）
- ❌ 只验"存在/非空"跳过语法校验（假完成最大漏洞）
- ❌ 吞掉工具失败记录（动作失败也是失败）
- ❌ 验证失败结果不带 degraded 标记静默交付
- ❌ 同一问题验证失败后仍继续（3 次后换方案）
- ❌ 静默吞掉承诺（reminder 验证器必须追踪）
- ❌ 大任务收尾不触发外部审计（自评盲区）
- ❌ 两轴审查合并/重排 findings（一轴掩盖另一轴）
- ❌ 表演性同意审查反馈 / 验证前盲目实施
