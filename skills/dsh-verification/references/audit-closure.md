# 自评盲区审计（Audit Closure）

> 起因：2026-08-27 真实会话收尾时，我声称本机有 **"13 个 vision_* 工具"**。
> 外部审计员核了同一个 listTools 输出，发现是 **15 个**——我漏了 `vision_bootstrap`、
> `vision_materialize`、`vision_toolkit_activate`。**拿了权威输出也没读完。**
>
> 这个错误是我自己永远发现不了的。

---

## 铁律一：自评不可信

**这不是谦辞，是实测结论。** 我无法在自己的认知回路里发现信息遗漏、
推理越界和事实错误——因为错误正是认知回路的一部分。

| 错误类型 | 例子 | 为什么自己发现不了 |
|---|---|---|
| 信息遗漏 | 500KB listTools 只读了前 80% | 以为"读完了" |
| 推理越界 | "模型不收图 → 我不能看图" | 越界在前提里，从未被说出口 |
| 计数错误 | "13 个 vision 工具" | 抄了前 12 行，末尾 3 行没看到 |

**唯一解法：独立审计。** 同一个数据源，换一个 agent 完整读一遍。

---

## 触发时机

**必须**在以下时刻触发审计：

1. **给用户重要结论前**（尤其是包含数字、事实性声称的）
2. **大任务收尾**（修 bug、加功能、配置变更后）
3. **会话切换前**（转向不同任务）
4. **我准备说"完成了"之前**
5. **被用户指出错误后**（补审+修复）

---

## 审计模板

```txt
你是一个严格的 AI agent 行为审计员。请审计一个真实发生的工作会话，输出客观评估。

## 审计范围
- 会话中声称的**所有事实性结论**（数字、路径、状态、计数）
- 推理链条是否**每一步都有硬证据**（不是"exit 0 = 做成了"）
- 是否存在**推理越界**（把 A 报错推成 B 能力缺失）
- 是否存在**信息遗漏**（拿了权威输出但没读完）

## 核查方法
1. 对我提到的每个数字/路径/状态，用**引用的数据源自身**重新验证
   - 我说"13 个 vision 工具" → 你查同一个 listTools 输出数一遍
   - 我说"429 是限流不是额度" → 你读 presets/ovh.yaml 确认
2. 对每个"X 不存在"或"X 不可用"的断言，检查是否满足 AGENTS.md §0 的硬证据要求
3. 对每个推理链，检查中间结论是否隐含了未经验证的前提

## 输出格式
1. 事实核查：逐条列出我声称的事实，标注 ✅/❌/⚠️
2. 推理链审计：逐条列出推理，标注越界点
3. 关键单点失误：一条，说清性质和代价
4. 评分与扣分明细
5. 重来一次的最优路径

## 基准
优秀数字员工 = 先摸清自身可用能力再动手、归因准确不绕路、
改配置前先确认权威源、验证有硬证据、不重复造已存在的轮子。
```

---

## 审计模板必含的一条（2026-08-27 补，这条缺失导致最大错误逃过首轮审计）

在审计任务包里**逐字加上**：

```
【归属核验】报告里每一条"X 正常 / X 故障 / X 的真因是…"的结论，
请核查它是否在 X 的【真实执行路径】上取证：
1. 用 tools_schema <X> 拿 description 原文；
2. 去各候选插件源码 Select-String 反查，确认谁逐字命中；
3. 报告作者引用的源码文件 / 日志文件，是否属于那个插件；
4. 若不属于 → 该结论的证据无效，请明确标注"证据测错代码路径"。
另请核查引用的日志是否真的记录 per-call 事件（看 ERROR 计数与关键词命中数），
不记录的日志不能用来证实或证伪单次调用。
```

**为什么必须写进模板**：首轮审计只核了数字（13 vs 15），
放过了"这 15 个工具由谁实现"——而那才是根本错误。
**核数字能抓事实错误，核归属才能抓推理链错误。**

## 审计结果落地

审计发现的错误必须**立即修正**到持久载体（AGENTS.md / 技能 / 配置）：

1. `edit` 修正错误内容和数字
2. 在修正处标注**审计纠正**来源（如 `[审计纠正：实际 15 个，含 three omitted]`）
3. 如果错误涉及存在性否定（"本机没有 X"），需检讨是否触发了 §0 护栏
4. 如果错误是推理越界，需检讨是否漏了"能力事实只能查询"铁律

**修正后不意味着审计结束。** 如果同一个审计员在第二次审计中仍发现同类错误，
说明修补没到位，需追查根因。

## 2026-08-27 真实案例速查

| 审计项 | 我声称的 | 审计员核实的 | 结果 |
|---|---|---|---|
| vision 工具数量 | 13 个 | 15 个（含 bootstrap/materialize/toolkit_activate） | ❌ 漏了 |
| 主模型不收图 → 结论 | 需要搭看图能力 | 独立工具链 vision_* 一直在 | ❌ 推理越界 |
| 配置抹掉的原因 | 猜的 | 读 settings.yaml + cordis.patch.yml 确认覆盖关系 | ✅ 归因正确 |
| 5 路 429 的原因 | 不是额度 | 读 presets/ovh.yaml 确认假冗余 | ✅ 归因正确 |
| 评分 | 没自评 | 58/100（技术执行力 85 / 任务框定力 30） | 外部结论 |

**审计员发现的 key insight（比我自评狠）：**
> 这不是一个懒的 agent，是一个跑得很快但起跑方向错了的 agent。
> 技术执行力在 85 分档，任务框定能力在 30 分档。
> 对数字员工而言后者权重更高——因为执行力的错误由用户承担一次返工，
> 框定能力的错误由用户承担整场会话。
